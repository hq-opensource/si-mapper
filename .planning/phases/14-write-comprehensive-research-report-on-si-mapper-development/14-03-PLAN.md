**\subsection{Development Methodology: Nine Experimental Iterations}**
- Opening paragraph: "The development of SI-Mapper followed an iterative experimental methodology. Over nine distinct iterations, the system architecture evolved from simple function-calling scripts to a sophisticated skills-based agentic AI system. Each iteration was driven by the failures and limitations of the previous one."
- Include the experiment-progression diagram: `\includegraphics[width=\textwidth]{experiment-progression.png}` with caption "Figure X: Evolution of SI-Mapper architecture across nine experimental iterations"
- Then narrate each iteration as a SHORT paragraph (3-5 sentences each). For each: what was tried, WHY it failed, and what was learned. Source: report/report.md

The 9 iterations (write these as prose paragraphs, NOT a bulleted list):

1. **V1: LLMs as Function Providers (Gemini 1.5 Flash)** — LLMs called for specific tasks (image recognition, text generation) within hardcoded Python logic. Business logic was hardcoded by the developer. Failed because: the LLM had no awareness of application context and could not make autonomous decisions. Used LangChain.

2. **V2: Workflow-Based Agents (Gemini 1.5 Flash, LangChain)** — Workflows defined step sequences for agents. More flexible than V1 but business logic was still hardcoded in workflows. LangGraph explored but abandoned due to high commercial licensing costs.

3. **V3: ADK Workflows (Gemini 2.0 Flash)** — Migrated to Google's Agent Development Kit (ADK). Still workflow-based with hardcoded logic. Introduced a local RAG system for documentation lookup. ADK was newly released with limited documentation; AI coding assistants could not help with the library.

4. **V4: Agentic Master Agent (Gemini 2.5 Flash)** — First true agentic attempt: a single master agent with full autonomy. The agent could make its own decisions. Failed because: prompts were too long and complex for the model to follow reliably. A simple while loop was not sufficient. Introduced the CopilotKit frontend and MCP tools.

5. **V5: Plan-Act-Review (PAR) Architecture (Gemini 2.5 Flash)** — Split execution into three sub-agents: Planner, Actor, Reviewer. Improved results but the agent terminated tasks prematurely. Adding a loop agent on top helped but was still insufficient.

6. **V6: Master + PAR Sub-agent (Gemini 2.5 Flash)** — Master agent delegated to PAR as a sub-agent. Both had full autonomy. PAR sub-agent still could not produce good enough results. Added tool call and state tracking to the frontend for visibility.

7. **V7: Master + Hybrid Workflows (Gemini 2.5 Flash)** — Replaced PAR with specialized image recognition workflows. Tried hybrid approach (workflow for recognition, agentic for planning). Neither fully workflow nor fully agentic. Results still not good enough.

8. **V8: Parallel Agents (Gemini 3.0 Flash)** — Introduced parallel execution: one specialized agent per equipment type running simultaneously. Significantly improved speed. Model upgrade to Gemini 3.0 improved accuracy. Also tested Gemini 3.0 Pro (better quality but much slower).

9. **V9: Skills-Based Master Agent (Gemini 3.1 / Claude Sonnet 4.6)** — Converted sub-agents into skills (inline instruction sets). Latest models powerful enough to follow detailed instructions without decomposing into sub-agents. Added visual self-correction via browser screenshots. Dramatically simpler architecture. This is the final architecture.

- Conclude with a paragraph: "The key insight from this progression is that advances in foundation model capability made simpler architectures viable. The skills-based approach became possible only when models like Gemini 3.1 and Claude Sonnet 4.6 reached sufficient instruction-following capability to execute complex, multi-step domain tasks within a single agent context."

**\subsection{Final Architecture}**
- Include the architecture diagram: `\includegraphics[width=\textwidth]{architecture.png}` with caption "Figure X: SI-Mapper final architecture — skills-based single master agent"
- Describe the three main layers in prose:
  - **Frontend (CopilotKit + Next.js):** Real-time agent HUD showing thoughts and actions, Graphivac CAD canvas for HVAC diagram visualization, Sigma.js graph viewer for the semantic model, code viewer for TTL and Python snapshots
  - **Master Agent (Google ADK):** Single LlmAgent with ~25 tools and 6 skills. Runs on Gemini 3.1 or Claude Sonnet 4.6. Maintains full context across the entire pipeline.
  - **External Services:** Neo4j graph database with Neosemantics (n10s) for ontology storage, Graphivac REST API for the CAD canvas

- Explain WHY this architecture was chosen (per user decision):
  - Single agent avoids coordination overhead between sub-agents
  - Skills provide domain expertise inline without the complexity of separate agent processes
  - The agent maintains full context across drawing recognition, grid placement, BACnet mapping, and ontology generation
  - Visual self-correction (screenshot + compare) is natural in a single-agent loop
  - Architecture is dramatically simpler to maintain, debug, and extend

**\subsection{Key Technology Decisions}**
- Brief paragraphs explaining WHY each key technology was chosen:
  - **Google ADK:** Provides agent lifecycle management, tool registration, session state, and artifact handling. Chosen over LangChain/LangGraph for lower commercial costs and direct Gemini integration.
  - **CopilotKit:** Implements the Agent-to-UI protocol for real-time frontend communication. Chosen because it bridges ADK's Python backend to the Next.js frontend without custom WebSocket infrastructure.
  - **Neo4j + Neosemantics (n10s):** Native graph database with RDF import capabilities. Chosen because ASHRAE 223P is an RDF ontology; Neo4j provides both storage and a mature query language (Cypher) for graph traversal.
  - **Mermaid/Sigma.js:** Lightweight, web-native visualization tools. Sigma.js renders large graphs with WebGL performance. Chosen over heavier tools (D3, Gephi) for simplicity and browser integration.
